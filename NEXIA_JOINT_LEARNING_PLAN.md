# NEXIA — PLAN DE DOMINIO CONJUNTO: CHATGPT + GITHUB
Status: ACTIVE / SAFE / ZERO-COST
Date: 2026-10-06

## Purpose
Convert Kael + NEXIA into a stronger operating team by learning the platform and the infrastructure together. The objective is not to "study everything" indiscriminately, but to master the capabilities that increase truth, execution, automation, resilience, speed and economic results.

## Principle
NEXIA learns the system and can execute/research within available capabilities. Kael learns the parts that require human control: account settings, permissions, approvals, external connections, UI actions, credentials, irreversible actions and strategic judgment.

## Track A — ChatGPT / OpenAI
Master in practical order:
1. Projects: instructions, files, sources, saved responses, project context and project organization.
2. Models and model selection: when to use each available model/mode and how to trade speed, reasoning and cost/limits.
3. Web search and source discipline.
4. Deep Research: planning, source restrictions, verification and reusable research workflows.
5. Agent capabilities, when available: safe delegation, browser interaction, limits and Human Gates.
6. Apps/connectors: available integrations, permissions, project use and security boundaries.
7. Files, documents, spreadsheets, code and artifact workflows.
8. Voice and multimodal workflows.
9. Automations/tasks: what can actually run, schedules, conditions, limits and failure modes.
10. Prompt/instruction engineering: project instructions, global instructions, reusable operating prompts and context architecture.
11. API / externalization: when ChatGPT should be an interface rather than the system of record.
12. Privacy, security, data controls, account/workspace permissions and recovery.
13. Product limits and pricing/usage constraints: measure and verify; never assume.

## Track B — Git / GitHub
Master in practical order:
1. Repository, files, commits, history and diffs.
2. Branches and safe change isolation.
3. Pull requests, reviews and merge strategy.
4. Issues, Projects and operational planning.
5. GitHub Pages and deployments.
6. GitHub Actions: tests, deployment and scheduled automation.
7. Secrets, permissions, environments and security.
8. GitHub API / CLI and integrations.
9. Codespaces / browser development.
10. Dependabot, code scanning and repository security.
11. Releases, tags, rollback and recovery.
12. GitHub Apps, OAuth and connector architecture.
13. Copilot and AI-assisted development, with review and verification.
14. Repository architecture for NEXIA Core as an external source of truth.

## Track C — Kael operating literacy
Kael does not need to become a software engineer. He should become capable of:
- locating and understanding the canonical state;
- reading commits/diffs and recognizing safe vs risky changes;
- opening/reviewing/merging a PR;
- managing project settings and ChatGPT permissions;
- connecting an authorized app/integration;
- recognizing when an action requires a Human Gate;
- understanding basic Git/GitHub terminology;
- reproducing a recovery procedure;
- checking whether a claimed automation actually exists;
- understanding the economics and evidence behind an experiment.

## Track D — NEXIA operating mastery
NEXIA should continuously test:
- available tools and actual permissions;
- safe automation opportunities;
- API/browser/connector alternatives;
- repository integrity and recovery;
- observability and telemetry;
- instruction/context efficiency;
- reproducibility and anti-duplication;
- evidence and unit economics.

## Learning method
No passive "course marathon". For each capability:
UNDERSTAND -> TEST SAFELY -> APPLY TO NEXIA -> VERIFY -> DOCUMENT -> TEACH KAEL ONLY WHAT HE NEEDS -> REPEAT.

Each module must answer:
- What can it do?
- What can it not do?
- What does it cost?
- What permissions does it need?
- What can go wrong?
- What can be automated?
- What should remain under Kael control?
- How does it improve NEXIA's measurable capability?

## Priority rule
Do not study a feature merely because it exists. Prioritize capabilities that remove a current bottleneck, reduce human work, increase evidence, improve resilience, unlock automation or improve economics.

## Human-learning contract
When Kael is needed, NEXIA should issue:
🔴 TAREA DE KAEL
with exact action, reason, cost (normally €0), risk, expected result and what NEXIA will do afterwards.

Do not make Kael learn something merely because NEXIA cannot be bothered to execute it. Human involvement is justified when the action is account-controlled, permission-controlled, security-sensitive, irreversible, or materially strategic.

## Success
The program succeeds when:
- Kael can operate the human-controlled surfaces confidently;
- NEXIA can exploit available machine capabilities without inventing permissions;
- the Core can survive interface changes;
- repetitive work is increasingly automated;
- new capabilities are evaluated by measurable benefit rather than novelty;
- the pair can diagnose and recover the system without reconstructing it from chat history.

## Source discipline
Use official OpenAI documentation for ChatGPT/OpenAI capabilities and official GitHub documentation for GitHub capabilities whenever possible. Record uncertain or undocumented limits as unverified until measured.
